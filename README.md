# rag-retrieval-eval

中英混合语料的检索评测：关键词、BM25、BGE-M3 向量、RRF 融合、RRF + bge-reranker 精排五路对照，跑在 77 道金标题上。每道题带逐字证据串，换线条件在跑数前写死，差值用配对 bootstrap 给区间。

*Retrieval evaluation on a mixed Chinese/English corpus (SEC 10-K excerpts plus Chinese Wikipedia). Five retrievers are compared on 77 gold questions: weighted keyword count, BM25 with jieba, BGE-M3 dense, RRF fusion, and RRF plus bge-reranker-v2-m3. Every gold label is backed by a verbatim evidence string. Decision rules were pre-registered before the first run, and differences come with paired-bootstrap confidence intervals. The question types are cross-lingual (Chinese question, English answer), terminology mismatch (Taiwan vs. Mainland usage), number provenance, and stale content (two fiscal years side by side). All numbers below come from a real run and can be reproduced with `make all`.*

## 为什么做：先评测，再选型

这套框架最初给一个私有知识库做：原来的检索是关键词加权计数，从没评测过，而「换成向量检索 / 上混合检索 + 精排」听上去理所当然。流程按下面四步走：

1. **先建尺子。** 先出金标题，每题带一段在答案段落里逐字存在的证据串，用脚本核对。
2. **再比较。** 五路检索在同一份语料、同一套题、同一个进程里跑，按题型拆开出表。
3. **判定条件提前写死。** 「什么情况下换线」在看到任何结果之前就写成文件，跑完照规则判，不在考题上调参。
4. **报区间，不报单点。** 逐题配对做 bootstrap，区间跨 0 就不算赢。

私有语料不能公开，所以这个仓库把语料换成公开语料、重新出题，再完整跑了一遍。

## 一条命令复现

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e ".[test]"
export SEC_USER_AGENT="Your Name you@example.com"   # SEC 要求写明身份；不设就直接走互联网档案馆快照
make all     # 下载语料 → 切段 → 核对金标 → 建索引并评测 → 前缀消融 → 生成 results/public/RESULTS.md
make test    # 单元测试 + 不需要模型的端到端冒烟测试
```

`make all` 依次做这几件事：
- `data/fetch_edgar.py`、`data/fetch_wiki.py`：按 `data/sources.toml` 钉死的版本下载 6 份 10-K 和 19 个中文维基条目。
- `data/build_passages.py`：切成 1,991 段，sha256 与 `data/manifest.json` 核对。
- `goldset/build_gold.py --check`：确认金标与重新解析的结果一致。
- `python -m rre.run_eval`：跑五路加三个变体。
- `python -m rre.ablate_prefix`：前缀消融。
- `python -m rre.report`：生成结果表。

模型名、设备、Qdrant 地址都在 `config.toml` 里，也可以用环境变量覆盖：`RRE_EMBEDDER`、`RRE_RERANKER`、`RRE_DEVICE`、`RRE_QDRANT`。`RRE_QDRANT` 可以是 `local`（本地文件，默认）、`:memory:` 或 `http://host:6333`。向量缓存在 `.work/`，第二次运行不会重新编码。

**本次运行的耗时（Apple M4 / 24GB，MPS，fp16）：**
- 编码 1,991 段：214 秒；无前缀版本再编一遍：290 秒。
- 主评测（含三个用精排的系统）：14.6 分钟。
- 下载 + 切段：几分钟，取决于网络。

**说明：** 写这个仓库的机器访问 sec.gov 被整体返回 403（SEC 对部分出口 IP 的限制），所以 10-K 是从 web.archive.org 的原样快照（`id_` 地址）下载的。`data/manifest.json` 记录的是这批文件的 sha256。理论上与 sec.gov 原文件逐字节相同，但我没能直接核对。

|---|---|---|

- 小节内拼到不超过 900 字，段与段之间不重叠。

| 题型 | 题数 | 问句 → 答案 |
|---|---|---|
| 跨语言 | 25 | 中文问句 → 英文 10-K 段落 |
| 术语同义 | 18 | 12 道台湾用语繁体（記憶體、奈米、執行長、輝達……）+ 6 道简体同义改写 → 大陆用词的维基段落 |
| 数字出处 | 18 | 中文问句带一个具体数字 → 原文出处（10-K 12 道，其中 3 道是换算写法；维基 6 道） |

## 结果（公开语料，可复现）

同一台机器上把主评测完整重跑一次（结果写到仓库外），8 个系统的全部准确率指标、过期内容指标和 bootstrap 区间逐位相同；只有延迟不同（重跑时机器负载更高，向量 P50 49 ms、RRF + 精排 P50 3,706 ms），表里的延迟取第一次运行。

数据来自 [`results/public/eval.json`](results/public/eval.json)，表格由 `python -m rre.report` 生成（[`RESULTS.md`](results/public/RESULTS.md)），逐题结果在 `per_query.jsonl`。指标按段落计算。延迟是单次查询耗时：进程内、模型已加载、每个系统先预热 5 题。

### 相对纯向量：配对 bootstrap 与预注册换线条件

换线条件（全部满足才换）：
1. ΔRecall@5 ≥ 0.03，且 95% 区间下界 > 0；
2. 任一题型掉分不超过 0.03；
3. P95 < 1,000 ms。

## 设计取舍

### 为什么提前写死判定条件

同一套金标题先用来诊断「为什么输」，再拿来调参数，就等于拿考题训练：一定能调出一个在这 77 题上更好看的配置，但那个提升说明不了什么。所以这里的做法是：
- 参数全部沿用私有语料上的值（BM25 k1/b、RRF k=60、每路 20、精排池 20、900 字分段），不在公开题上调。
- 三个变体在私有语料上就预注册过，这里原样复用。
- 换线条件和预判写成文件，记下题目与段落文件的 sha256，然后才跑第一次。

代价是：有些明显的改进方向（比如精排池改成 10、精排截断到 256 token）这里没试。试了也只能算新的探索，要换一套题来确认。

### 为什么混合检索没上线

**私有语料上（2026-09）：** RRF + 精排的 Recall@5 0.641，纯向量 0.643，打平；但单题慢约 37 倍，还多一个 2.3GB 模型。拆开看，损失全在跨语言题，机制有两层：
- BM25 用中文问句打不中英文原文，等权 RRF 把它的无关结果掺进精排池，挤掉了原文；
- 精排又偏好同语言的中文复述页。

所以上线的是纯向量。

**公开语料上（本仓库）结论不同：**
- 精排把 Recall@5 从 0.661 拉到 0.779（区间 [+0.044, +0.199]），V1（精排池只取向量前 20）拉到 0.878。
- 差别可能在中文侧（这是推测，没有单独验证）：维基条目只是泛泛介绍公司，不像私有库那样有逐条复述英文原帖的中文笔记，交叉编码器比较容易分清「讲的是这件事」和「讲的是这家公司」。
- 不过按预注册的条件，这次仍然不换线：P95 3.7–4.9 秒，远超 1 秒；而且术语题从 1.000 掉到 0.944（18 题里掉了 1 题），超过 0.03 的容差。

这条结论的含义是：精排值得做，但要先解决延迟。可以截断输入、缩小精排池、换小模型或常驻 GPU 服务，然后用新的一套题重新验证。

还有两点：
- **不精排的 RRF 两边都是最差的融合方式**（这里 0.420，比纯向量低 0.241）。BM25 在跨语言和过期内容题上近乎噪声，等权融合等于把噪声掺进来；降权到 0.5（V2）也救不回来。
- 两份语料给出的「精排有没有用」相反。所以这类结论不能从别人的 benchmark 搬过来，要在自己的语料上量。

## 失败案例

1. **BM25 在中英混合问句上被中文词淹没，预判错了。** NS-07 问「美光说自己持有约 14,500 项有效美国专利，出自年报哪一段？」：
   - 数字 14,500 整体成词，答案段落也确实含这个词。
   - 但问句里的「美光」「专利」「年报」在中文维基的美光条目里出现得多，十几个中文词的分数加起来压过一个数字词，金标排在第 35 名。
   - 12 道 10-K 数字题都是这样：BM25 只有 2 道进前 5。纯中文的 6 道维基数字题，BM25 都排进前 2。
   - 私有语料上 BM25 在数字题很强，是因为那里问句和答案同语言。
2. **向量检索：同语言的泛泛介绍压过外语原文。** CL-01「英伟达自己有晶圆厂吗？芯片交给谁代工？」：
   - 前几名全是中文维基「英伟达」条目（它确实讲了代工），10-K 原文排在第 31 名，精排池（前 20）都没进，所以精排也救不回来。
   - CL-14（美光网络安全由哪个委员会监督）同样排在第 26 名。
   - 这和私有语料上「中文蒸馏页压过英文原帖」是同一个机制。
3. **精排让「先读到旧数字」更常见。** 过期内容题上：
   - 纯向量把上一年年报排第 1 的比例是 0.250，RRF + 精排是 0.500，V1 是 0.562。
   - 精排把两年的对应段落都提到前面，但分不出哪年是新的，问句里也没给年份。
   - 例如 ST-16「苹果的登记在册股东人数」，三套系统第 1 名都是 FY2023 的 23,763，FY2024 的 23,301 排第 2。
   - 检索层没有「时间」概念，要靠排序时按文档日期加权，或者在答案生成阶段核对年份。这里都没做。
4. **换算写法的数字只有语义检索接得住。** NS-01「470 万开发者」（原文 4.7 million）、NS-06「33.4 亿美元」（原文 $3.34 billion）、NS-10「142 亿欧元」（原文 €14.2 billion）：BM25 分别排第 121、212 名和没找到；向量排第 1、5、1 名。

## 局限

- **样本小。** 77 题，按题型 16–25 题；术语题只来自 19 个维基条目，数字题和过期内容题只来自 3 家公司、2 个财年。按题型的数字一题就能动 0.04–0.06。
- **金标仍是人判。** 证据串机制保证「金标段落确实含答案」，不保证「别的段落答不了」。出题过程中已知有几处可能的漏标（见 `goldset/README.md`），漏标会让所有系统一起偏低。
- **出题人见过语料。** 题目由人和出题助手对着段落写，问句的措辞会不自觉地贴近答案段落。过期内容题用模板出题，就是为了减少这种偏差。
- **过期内容题混入了跨语言因素。** 模板问句是中文、答案是英文，关键词和 BM25 在这类题上什么都找不到，所以这一类只能比较语义检索之间的差别。
- **延迟只代表这一台机器。** 数字来自 Apple M4、MPS、fp16，换 GPU 或 CPU 会差很多。fp16 在 MPS 上的数值也可能让个别名次在不同机器上有出入。
- **关键词基线是移植版。** 原工具按文件打分（文件名 +100），这里改成按段落打分，用前缀代替文件名。它代表「这类打分方式」，不是原工具逐字复刻。
- **维基渲染不完全确定。** 同一 revision 在不同日期渲染，「X 年前」一类模板的输出会变，所以维基文件的 sha256 只做提示；金标由证据串逐字核对。

## 私有语料上的结果（不可复现）

| 系统 | Recall@5 | Hit@5 | MRR@10 | P50 / P95 |
|---|---|---|---|---|
| 关键词加权计数（原工具） | 0.321 | 0.463 | 0.398 | 92 / 295 ms |
| BM25（jieba） | 0.468 | 0.574 | 0.557 | 2 / 8 ms |
| 向量（BGE-M3） | 0.643 | 0.815 | 0.678 | 154 / 220 ms |
| RRF 融合 | 0.553 | 0.694 | 0.588 | 182 / 259 ms |
| RRF + bge-reranker-v2-m3 | 0.641 | 0.796 | 0.675 | 5,726 / 12,307 ms |

当时的结论：
- 上线纯向量（Recall@5 0.321 → 0.643）。
- V1 变体 +0.026，区间 [−0.040, +0.091] 跨 0，且 P95 5.2 秒，不换线。
- 前缀消融 0.643 → 0.563，区间 [+0.025, +0.136]。
